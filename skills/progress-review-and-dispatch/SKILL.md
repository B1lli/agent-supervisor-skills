# 批量盘点与推进（总管方法论）

这个 skill 干两件事：**把当前所有推进项定档**，然后**把该做的动作立刻做掉**。
只汇报不推进，等于没用。

## 一、先按目标分组，不按模块分组

先给这项工程定 2–4 个目标，报表一律按目标分组；目标由工程自己定。示例（一个「给收件箱自动分类」的功能）：

- **(a) 该分类的邮件正确进桶，分错的少**
- **(b) 规则该生效时生效，不该生效时不误伤**
- **(c) 用户确实因此少花时间，而不只是看着有了分类**

按模块分组会让用户看不出"哪个目标现在是瘸的"。

## 二、动作路由表（每档 = 一个下一步动作）

**图标只有三种，一眼看谁在动、谁卡着、谁完事了：**

| 图标 | 含义 | 用在哪些档 |
|---|---|---|
| 🔄 | **推进中**——有人在干，不用管 | 2、2.5、3、4、6、7 |
| ⚠️ | **阻塞**——卡住了。**若卡在用户身上就等用户回答；否则总管必须亲自推进，不许挂着** | 5、以及任何"说了要派却没派"的 |
| ✅ | **已完成**——已上线且复验过 | 1.5 复验通过后 |

| 图标 | 档 | 含义 | 下一步动作 |
|---|---|---|---|
| 🔄 | **0** | **决定不做** | 无动作。但必须写**理由**和**重评触发条件**（例："挖掘还没通电，通电后重评"）。**"决定不做"和"忘了做"必须分开** |
| ⚠️ | **1** | 已验证，可部署 | 部署（**等用户批准 ⇒ ⚠️**）。**必须标证据强度**：自评 / 隔离栈 / 真实语料回放 / 生产 A/B |
| 🔄 | **1.5** | **已部署，未复验** | 派复验。**不等流量**——拿存量语料回放（团队有回放测试 skill 或脚本就用它）。复验通过后才配 ✅ |
| 🔄 | **2** | 写完了，没验 | 派验证 |
| ⚠️ | **2.5** | **写完了，人跑了，结论没交回来** | **总管亲自去捞成果**：执行线常在系统临时目录自建 `git worktree`，先去那儿找（**别只看派卡时自带的工作树目录，那里基线往往陈旧**），有成果就另起一个任务接手。**这一档不许只记录不动手** |
| 🔄 | **3** | 方案已证伪，正在重修 | 等重修完重测。**旧的绿不能当今天的绿**（尤其分支落后集成分支很多时） |
| 🔄 | **4** | 发现问题，没开修 | 派修复 |
| ⚠️ | **5** | 卡住了 | **写清卡在谁身上**：等用户拍板（⚠️ 等回答）/ 等部署 / 等另一条线 / 门挡住（**后三种总管自己推**） |
| 🔄 | **6** | 只有现象，没根因 | 派查根因 |
| 🔄 | **7** | 连是不是问题都不知道 | 派测量 |
| ✅ | — | 已上线 **且** 复验过 | 无动作，归档 |

**⚠️ 的纪律**：报表里每出现一个 ⚠️，正文必须回答"**在等谁**"。
只有"等用户回答"这一种可以挂着；其余（等部署、等另一条线、门挡住、结论没交回来）
**都是总管自己的活，报完这一轮就得动手**。

**6 与 7 的判据**：手上有没有一个**能报非零**的量具？
有量具但读数是零 ⇒ **7**（先证明量具在已知正例上能报非零）；量具正常、读数确实异常 ⇒ **6**。

**另加一栏「认知」**（与档位正交，一个词）：**现象 / 根因 / 已证**。
有了它就不必写"6→2"这种箭头——箭头一出现就说明单一维度不够用。

## 三、报数之前的四问（违反任何一条就别报）

> **#1 和 #2 是同一个病：一个总数没拆。** 拿到任何「N 条 X 有问题」，**动笔前先各拆一刀**——
> **`group by 天`**（还在发生，还是死账？）和 **`group by 归属`**（真人，还是测试账号？）。
> 这类错栽过不止一次，每次都是没拆：一批「永久丢弃」里大半是测试账号 / 一批「缺日志」里绝大多数集中在某一天的单日爆发 /
> 一批「就快丢了」的记录实际早被队列游标推过。**别指望临场想起来，把这两刀当成写字之前的固定动作。**

1. **这些还会再发生吗？** 还是已经被钉死成历史残留、永远不会再动了？
   （实例：一批观察看着像"差一次就丢"，实际早被队列游标跳过，再也不会被处理——**是死账不是风险**。）
   **判据**：按天拆开，看**最近几天是不是已经归零**。若某一天占比超过 X 成、而最近 N 天为 0（X 与 N 按自己业务定），
   正确写法是两句——①「某日曾有一批，属历史残留」②「该现象近 N 天为 0，当前无此问题」，
   **不许合成一个吓人的总数**。
2. **是谁的？** 真实用户 / 测试账号 / 无主 **必须分列**，不许只给总数。
   （实例：一批丢弃记录里几乎全是测试账号，真实用户只有个位数——**量级能差一两个数量级**。）
   **测试账号判据必须覆盖全部命名约定**——只按一种前缀、或只看邮箱含 test，会漏掉一整类；先摸清库里实际用过的测试账号命名再写判据。
3. **量具本身会不会是坏的？** 两种最常见的坏法：
   - **一个都没有，所以"全都符合"**——查"这批失败是不是全是同一个原因"时，如果某条压根没有失败记录，
     它会被算成"全符合"混进来。**筛之前先把空的排掉。**
   - **它从来就没报出过非零**——先拿一个**已知肯定该报的例子**喂给它，报不出来就说明尺子坏了，
     不是"真的没问题"。
4. **这条路失败的时候，是"报错"还是"正常收工"？**
   如果它把失败包装成一个正常的结局返回，上游会当成功处理——那么**所有靠"报错/异常/失败计数"
   来发现问题的监控都看不见它**。
   （实例：一条后台处理链路在多次让位后以"正常终态"收口，上游当它处理成功、游标照常推进，
   于是异常计数恒为 0——**看着一片太平，实际那批数据已经丢了**。）

> 真实教训：同一天两次拿没拆干净的数汇报——一次把已被游标推过的死残留报成"一批看着就快丢了的记录"，
> 一次把一个总数报成同样多的真实用户（实际真人只有个位数）。**数对了，话错了。**

**报"丢失"前还要多问一句：排除"用户自己删的"了吗？**（查软删除记录表；删除会级联带走来源行，
和"系统丢了"在数据上长得一模一样。）

## 四、推进：派活之前先判依赖，别只写"撞文件即停"

**"撞文件即停回报"不是依赖管理，是把冲突推给执行线现场处理。** 派之前先判：

1. **有没有活着的相关会话？** 先看还有哪些会话可寻址。
   **能发消息就别新开**——新开会丢掉它脑子里的试错过程。
   （注意：后台任务的进程一结束就不可寻址，只能另起一个任务接手；此时把已验证的证据搬进新任务书，
   减少重新推导。）
2. **现在做会不会白做？** 若上游那条线会改变"哪些东西还需要做"，就先等。
   （例：门收窄那条会改变哪些测试还跑不跑，在它落地前清红测试是白干。）
3. **同文件冲突要定序**，不要并行。定完序写进各自任务书。

## 五、什么时候该合并验证，什么时候必须分开

**合并的判据不是省时间，是"效果互相影响"。**

若 A 的效果会改变 B 的表现，分开测会得出**误导性结论**。
> 典型：并发槽位被僵尸任务占着时，单独测队列并发化 ⇒ 得出"并发化没用"的错误结论。

**合并后如何保住归因——逐条 revert 检验：**
1. 合并树跑一遍记基线；
2. 逐条 revert 掉某修复 ⇒ **它自己的场景必须变红，其余保持绿** ⇒ 恢复 ⇒ 再绿；
3. **某条 revert 后场景没变红 = 该条判 UNPROVEN**（要么测试没测到它，要么它没起作用），**不许判 PASS**。

这比分开跑更强：同时证明了"该修复在合并环境下仍然有效"。
**合并冲突要逐处记录**——冲突解法本身是没被任何人验证过的新代码。

## 六、任务书必带的硬约束（漏了会让执行线返工）

- 生产库只读；不部署；不改线上运营配置表（除非用户单独授权）。
- 需要登远端时把完整命令写死在任务书里，并清掉会干扰的代理环境变量（形如 `env -u HTTP_PROXY -u HTTPS_PROXY ssh -F <配置> <主机>`）。
- **开工自建树** `git worktree add --detach <路径> origin/<集成分支>`，
  **别用派卡时自带的工作树**（基线可能落后上千提交）；**回报第一句写实际 HEAD 与落后集成分支多少提交**。
- 仓库里若有软链形式的包或已生成的产物，写明**不要重新生成**；跑测试前先看一眼 `.env*`，有会干扰的先挪开。
- **外部依赖子仓必须先装依赖**——不装会让端到端测试的前置步骤红，**看着像门坏了其实是缺依赖**。
- **禁止 `--no-verify`**；门抖就重跑（把已知抖动率和**重跑上限**写进任务书，例如上限 5 次）；
  真过不去回来找总管，按先真修两次、仍过不去才由人工放行的流程走，不自行豁免。
- 端到端测试**报告绑精确树态**：先把树定型再跑，跑完别再改文件；铸证据标记前还原测试自己改写过的生成物（如前端路由表这类自动生成文件）。
- **不得对外发布任何内容**（禁止任何 `gh` 写操作、PR、issue、评论、外部服务）。
- `codex exec` 的 heredoc 必须 `< /dev/null`；判挂死用**墙钟涨 + CPU 不动 + 无活子进程**三者一起看
  （单看 CPU 会假阳性，PID 可能已被回收）。
- 逐层报 **PASS / FAIL / UNPROVEN**；**不许给一个总的"都过了"**。
- **只在必要时联系总管**：任务书必须写明——只有①被真正卡住且需要总管决策（要碰别的线正在改的文件、要越出授权、门连续过不去）②最终交付，才发消息；
  **不要发进度汇报**（"我开始了""在跑第 N 轮"）。总管用只读方式观察进展（worktree 的 `git log/status`、分支 ahead/behind、
  读数文件里的 verdict、证据目录的文件名与 mtime、只读查库），**不打扰执行线的迭代**。
- **不许下强制中断点**（"先报我再动手"）。要控风险就给**边界**（哪些文件不许碰、碰到停下问），不要给**打卡点**。
- **设计类任务书必须写死交付物边界**：「交付物只有 `<文档目录>/*.md`（+≤200 行接口草案）；出现任何数据库迁移、应用代码、外部依赖目录的改动即越界，立即停手导出为 patch」。
  （真实案例：某设计线在决策点还没拍板时就提交了数据库迁移、写了产品代码、把外部仓库快照放进树——执行线会把"做完"理解成"做到能用"。）
- **推送权不靠措辞**：任务书写「完成后只回报 SHA，推送由总管核证据后执行；执行 `git push` 到集成分支/发布分支/主干视为越界」。
  （真实案例：一天内两条线直推集成分支，"不推远端"四个字挡不住完成惯性；真正管用的是一道在工程上强制的推送闸门——推送必须先过一次人工放行。）
- 容器/预发/浏览器/API 测试走团队统一的测试 skill 与命令，任务书里写死；不允许各线自己拼本地栈起法。

## 七、部署与保底

- **回滚牌必须在 build 之前打**（`:latest` 被覆盖后旧镜像不可再 tag）；打完**回读确认**。
  注意别拿错牌——上一趟的牌指的是上上个版本。
- 镜像必须把**完整提交 SHA** 作为构建参数注进去，否则健康检查里的版本字段是空的、部署无从验证。
- **唯一成功判据 = 健康检查返回的版本 == 目标 SHA**。
- 部署后复验（关键链路跑通、关键字段落库）→ 拿到证据 → 晋级到发布分支/稳定标签。
  **晋级脚本强制要求附上证据，不许绕**——它挡住过总管本人，这正是它存在的意义。

## 八、输出格式

按 (a)/(b)/(c) 分三张表，每张表列：**事项（大白话）| 档 | 认知 | 完整状态与立即步骤**。
- **说人话**：讲原因、前后变化、举例子，**不堆变量名**。
- **每段自包含**：没读过任何上文的人也能一瞬间看懂本段——每段开头先用一句话把问题本身讲清，再讲进展。
- **写增量，不写状态**：只写本期改好了啥/修了啥/新增了啥。「某开关还关着」「某问题还在」是状态不是进展，不许单独成段；若必须提及，改写成本期为它做成了什么（如「新增了实证案例与拍板材料」）。
- **不用贬损表述**：不写「推倒重来」「烂摊子」这类词，写「重写为…」「统一为…」。
- **不用比喻和黑话**：「给摆锤装了仪器」这类比喻禁用，一律通用常见表述（如「新增一套双向回归检查」）。
- **效果先行**：每段第一句必须是效果陈述——「现在能拦住…」「不再会出现…」「仍不能…」，然后才用一两句讲做法。上级要听达成了什么效果，不想先听你干了什么、怎么干的。
- **阻断项必须单列成节**：修复未启用、验收结果未出、决策未拍、功能牺牲中，全算阻断，一项不许漏。一份全绿的报告默认可疑。
- **只有改变了系统行为或能力的才算进展**：「记录了一个案例」「整理成了拍板材料」「备好了方案」都不算；已知问题再次发生更不算。把这些包装成进展=虚报。
- **措辞不依赖内部语境**：「线上复测」这类内部短语要写成人人能懂的（「部署后在测试站按用户真实操作重走出问题的场景」）。
- 每项状态写**完整一句**，不写"同上"。
- 表后给一句**"现在最该做的一件事"**，并说明为什么是它。
- **报完就把动作做掉**：该派的派、该发消息的发、该部署的部署。只报不动等于没做。
