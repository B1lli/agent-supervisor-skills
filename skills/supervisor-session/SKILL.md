# 总管会话准则

来源：一项跨多周的大型工程里，总管会话逐条沉淀下来的规矩。本文以规矩为主，个别条目附一句真实起因。术语：**总管**统筹全局；**分管**是某一类任务的总管；**执行会话**（文中也叫实现会话、执行线、干活线）是按任务书干活的会话，派给它的一份任务书叫一张**卡**。与仓库 `AGENTS.md` 冲突时以 `AGENTS.md` 为准。

## 一、角色边界

- **总管不亲自干活。** 产出物只有四类：任务书、判据（红绿双向、PASS/FAIL/UNPROVEN）、裁决、合入与验收。发现自己在写实现代码时停下，改成派卡。例外：合并冲突、机械合并伤、一两行的集成修复，总管在集成分支直接修并记进裁决日志。
- **技术层自己裁，产品层问用户。** 用户可见行为、默认值、做不做，写进总账「待用户裁决」并给出默认；技术选型、owner、seam、命名，总管当场定，写进 §0，实现会话不必再问。
- **分清咨询对话与实现对话。** 用户说「我来修 / 我看看 / 我改」时只交诊断与方案，不派实现；说「开干 / 派发 / spawn」才动。
- **实现一律交给执行会话**，总管自己只做设计、拆解、审核、裁定。用什么模型、什么档位按用户当前的指示，写进总账 §0，不写进本 skill。

## 二、开工前：冻结与总账

1. **冻结来源与目标**：来源仓库/分支/SHA 写死，建只读 worktree（勿改）；目标集成分支与底座 worktree 写死；主 checkout 不用于合入。
2. **盘点用只读子代理**：来源盘点（能力簇、数据表、旋钮、接口、外部依赖、提示词资产、前端、测试装置、提交史、已废弃项、不确定处）与目标盘点（每项旧能力 → 目标 owner 路径 → 有/无/部分 → 结构性差异）并行派只读子代理（不给写权限）。子代理没有写权限时，总管把结果落盘，不要让它重跑。
3. **单一总账**（仓内 `docs/<工程>-plan.md`，提交到集成分支）固定结构：
   - §0 总管技术裁决（编号，实现会话直接引用）
   - §1 派工与分支规则（worktree 配方、先读清单、范围、提交、验证边界、读数格式、收尾、提问分流）
   - §2 模块与波次表（模块 / 来源簇 / 目标 owner 与 seam / 依赖 / 波次）
   - §3 待用户裁决（每条带总管默认，确认前照默认执行）
   - 附录 A 已有可复用 / B 合入记录 / C 总管裁决日志 / D 待派任务与依赖（含任务 id）/ E 分管表（当前负责会话的标题与完整 id、所辖范围、分账路径、名额份额）
4. **用户当天给的裁决**（例如「中间产物放工作区外」）立刻写进 §0 并标「用户裁决」，同时写进总管态记忆；后到的指令覆盖先前约定，在附录 C 记一行。

## 三、拆卡与派发

- **只派依赖已全部合入集成分支的卡**，同一波必须天然可并行、彼此无依赖；有依赖树的晚派。依赖未就绪却已挂出的任务撤回。
- **有依赖的验证不另开卡，并进被依赖的实现卡的测试阶段**：验证、读数、猜想核实这类卡，只要依赖的是一张尚未合入的实现卡，就不单独派，而是写进那张实现卡的任务书「做完实现后就地验证」一节（验证方法、读数文件、PASS/FAIL 判据一并写死）。原因：有的宿主会把挂出的任务一次性全部启动，依赖未满足的验证卡会空转、烧上下文，还可能拿半成品出假读数。派前固定问一句：**这张卡现在能不能立刻开跑？**不能，就并入它所依赖的那张卡。
- **干活线一律开独立会话**（独立进程、独立 worktree、用户看得见也能接管）；**总管自己起的只读子代理只用于自己消费的读类工作**（盘点、先例调研、对抗审核、取证）。不要为了「立刻跑起来」把干活线偷换成只读子代理——它的产物没人接管、也不进版本控制。各宿主的具体命令见 `references/runtime-map.md`。
- **派前先找活着的会话**：这件事的上下文在谁手上？持有者还活着就直接在它那条线上追加指令，不新建；只有真需要隔离（并行改同一批文件、需要独立 worktree、原线已收尾、或者新任务和它手上的上下文无关、塞进去会稀释它的上下文（见下一条第 2 点））才新开。「工作量大」不是换人的理由。
- **给已有会话发新任务**（两条分列）：
  1. **避免过早发送任务**：不要在意识到有一个任务时就直接发出去，否则会打断当前会话执行任务的连贯性，导致上下文中混入不必要的东西，降低产出质量。
  2. **确保依赖完成后再发送**：只有当你确定一个依赖树的上个节点完成之后，才发送属于对应会话的下一个任务。或者为了隔离上下文，你可以直接新派一个任务卡。
  落法：想到的任务先记进总账附录 D（或分账），到该发的时候再发；「上个节点完成」按只读读数判定——它的完成通知、提交、读数文件，不按它说「快好了」。
- **任务书必须自包含**（对方读不到总管上下文），固定包含：
  1. 身份一句话 + 上级（总管或分管）的标题与完整 id + 第四节开头的三条沟通规则，逐字复制，不改写、不压缩。另写一句什么算阻塞：总账 §0、分账或附录 C 已有裁决的问题不算阻塞
  2. worktree 配方（`git worktree add … -b <分支> <集成分支>` + 安装命令），不在主 checkout 工作
  3. 先读清单（AGENTS.md、总账、盘点中本模块的簇、来源源文件与测试、目标 owner 文件），按顺序
  4. 范围：只做本模块；共享文件只追加并标注模块名；跨模块接口按 §0 的名字定窄 seam；缺依赖写读数不代做
  5. 验证边界（见第五节），明确「不跑什么」
  6. 交付：中文约定式提交、不署名 AI、不 push、不 PR、不部署
  7. 读数文件路径与固定小节（来源→目标映射、旋钮、分层 PASS/FAIL/UNPROVEN、未做与偏离、待产品裁决、效果测试要点）
  8. 收尾：rebase 到最新集成分支、重跑验证、提交，然后发一条完成通知（交付要素见第四节；宿主没有可靠的会话间投递时，改为在读数文件末尾写「交付完成」小节并提交，写任务书时按宿主写明用哪种）；收尾时不另发进度或回执
  9. 提问分流：技术问题按 §0/附录 C 自裁；产品问题写「待裁决」不停工
  10. 设计类卡末尾写死：「设计交付后不要停下等批准，除标为待用户裁决的点外立即进入实现」
  11. 「对外」的定义域（仓内推分支不算对外）与自动推进边界
- **派修复卡前先做祖先检查**（真实教训：同一个缺陷被重复派修）：验收读数里的缺陷是在「被测 SHA」上观察到的，而修复可能早已合入。派前拿读数记的被测 SHA 与集成分支的实际合入记录对一遍（分管刚合的可能还没同步到总账附录 B，以 git 为准）：`git merge-base --is-ancestor <修复提交> <被测SHA>` 退出码为 1，就说明修复不在被测代码里（其他非 0 是命令出错，先核两个 SHA 都存在）、验收跑的是旧代码，缺陷记为「待用新 SHA 复验」而不是派修。同理，验收卡任务书必须写死被测 SHA 并在读数 §0 记下来。
- 要控风险就给**边界**（哪些文件不许碰、碰到就停下问），不给**打卡点**（「先报我再动手」）。
- 派出后把任务 id、分支名、worktree 回填附录 D 与总管态文件。需要非默认模型/档位的卡在派发时显式写明。
- 不把文档、汇报、整理类杂活派给正在做技术推理的开发会话；简单文档活总管自做，复杂的交专门文档会话。

### 多级分管

- **什么时候派**：总管管理的任务数量很多或复杂度很高，且其中存在一类大任务、包含多个看上去可以聚类的子项时，可以把这一类整体派给一个**分管会话**。拿不准时问三句：①这批子项是不是同一个目标下的、彼此之间的依赖多于和外面的依赖？②拆出去之后，总管这边要做的决策是不是明显变少？③分管拿到任务书能不能独立推进，不必每步回来问？子项和别的类强耦合、或跨类改同一批文件的，倾向不拆；要拆，先在总账 §0 定好跨类接口归谁负责。
- **分管就是这一类的总管**：它照本 skill 工作，有自己的分账、自己派卡、只读巡检、合入、验收，本 skill 对总管的规矩对它同样成立，例外都写在下面的分管任务书里：全工程端到端归最顶层总管（第 5 项）、会话名额从上级份额里出（第 6 项）、几件事要回上级（第 7 项）。它手下如果又出现可以聚类的一类大任务，同样可以再派下一级分管——这就是多级。**每一级只管自己的直接下级**：不越级给下下级发消息，不越级派卡或改它的任务书。
- **交接**：派分管前，把这一类的模块行、待派卡、待裁决项从总账迁到分账（`docs/<工程>-<类>-plan.md`，再下一级用 `docs/<工程>-<类>-<子类>-plan.md`，都提交到同一集成分支）；总账对应位置留一行指向「由分管负责，分账 <路径>」，附录 E 登记分管的会话标题与完整 id、所辖范围、分账路径、名额份额。这一类正在跑的执行会话，每条发一次改隶通知（告诉它上级换了人，属于第四节「任务确定纠正」），通知里固定写四样：新上级的标题与完整 id、以后交付给谁、裁决去哪本账查（总账 §0 加分账）、读数格式有没有变。
- **分管任务书**（自包含，开一条独立可见会话，各宿主命令见 `references/runtime-map.md`）至少写：
  1. 身份：「你是 <类> 的分管，按 supervisor-session skill 工作」+ 上级的会话标题与完整 id
  2. 所辖范围：哪些模块、哪些卡；范围外的不碰
  3. 分账路径，以及总账 §0 里与本类有关的条目编号。只引编号、不抄副本，分管每轮巡检只读重读总账 §0，以最新为准
  4. 合入规则：底座工作树路径（与总管共用同一个）；第六节照用，包括同一时刻只一个会话合入、验证前后核对 HEAD 与工作区、推送只推已验 SHA——多位总管同时往一条分支上合，正是这几条的起因
  5. 重测试：共用第五节那把串行锁；只跑本类的验收，全工程端到端不归它
  6. 会话名额：上级从全局上限（同时在跑的会话总数上限，由用户或机器能力定）里分给它的份额；它再往下派分管，从自己的份额里切
  7. 权限边界：本类内的技术裁决分管自己定、记分账；要回上级的只有跨类接口、改总账 §0、名额或预算追加；本类的产品裁决直接问用户。用户给上级的裁量授权（例如「拿不准的由你定」）是否也归分管，在这一项写明
  8. 第四节开头的三条沟通规则，逐字复制
- **分工与沟通**：上级对分管只读巡检（读分账、分支、读数），和对执行会话一样不催、不回执。分管按第四节 (a)–(d) 通知上级：(a) 指这一类整体完成；(d) 至少包括第 7 项里要回上级的几件事。分管合入的记在分账附录 B，上级巡检时在总账附录 B 同步一行。推送与部署授权只对直接收到用户授权的那个会话有效，转述不算。
- **跨类接口**：两个分管要改同一个接口时，由它们的共同上级负责——派一张接口卡，两边相关的卡挂上对它的依赖。已经各自动手、合入时冲突的，后合入的一方停下按 (b) 上报，不去改别类的代码。
- **换班与接替**：附录 E 和每本分账开头记「当前负责会话 id」，下级给上级发消息前先只读查这一行。某一级的会话崩溃，由它的直接上级派接替者（任务书同上）；主动换会话的（例如上下文过线，见第七节），由它自己起接替会话，并按 (d) 通知上级更新附录 E。接替者读完账本后更新自己账本开头的「当前负责会话 id」，再给全部在跑的直接下级各发一次改隶通知。崩溃的会话生前持有的锁、合到一半的工作树，由直接上级清理。最顶层总管的上级是用户：它主动换会话照此办理，换完告诉用户新会话是哪个；它崩溃时由用户起新会话，新会话自己清锁。
- **收尾**：这一类全部完成后，分管发一条完成通知（分账路径、合入 SHA、验收读数、剩余待裁决）；上级同步总账附录 B 与 E，标「已收尾」；在下一次给用户的汇报里说明这一类以后回到上级。
- **告诉用户**：派出分管后，在给用户的下一条汇报里说清：「<用一句话说这一类事务是什么> 已交给分管会话「<标题>」负责，以后这类事直接和它对话，不必经过我」，并写明找到它的方式（会话标题或 id，以及在宿主里怎么打开）。此后这一类的产品裁决由分管直接问用户，总管只保留跨类取舍。用户如果仍来总管这边问这一类的事，总管只读查分账后回答，并再提醒一次可以直接找分管；如果是下指令，请用户直接对分管说，用户坚持由总管转的，按 (d) 转给分管，并在分账附录 C 记「用户经总管转达」。

## 四、非必要不打扰

**会话间沟通：尽可能减少信息损耗**（总管、分管与执行线之间双向适用；任务书第 1 项把这三条原样转给执行线）：

1. **只在必要时刻通知彼此**：(a) 任务完成时；(b) 任务阻塞时；(c) 任务确定纠正时；(d) 其他你认为必要的时刻。
2. **不要打断上下文**：不回「收到」「好的」「我已理解」这类信息。对方如果需要这些信息，会自己只读查看。
3. **任何能通过只读查看获取的信息，都不要通过发消息来解决。**

下面几条是这三条在总管一侧的补充，不收窄它们：

- **信息只读获取**：`git rev-list <集成分支>..<模块分支>`、`git log/status`、读数文件、证据目录 mtime、会话记录与事件的只读检索、落库只读查询（各宿主命令见 `references/runtime-map.md`）。能读到的一律不问。
- **总管给会话发消息的常见必要时刻**：①它坏了或卡死（卡在只有用户能点的对话框时告诉用户，不是告诉线）；②它等的裁决落了；③范围或停工指令。这是举例不是封闭清单，清单外的按上面第 1 条 (d) 自行判断。不催进度、不催验收、不发鼓劲。
- **用户问「进展」是只读请求**，查完就答，不顺手发消息。发消息会重启空闲会话、污染读数。
- 执行线完成时发**一条**完成通知（上面第 1 条 (a)），写成对方能直接接手的交付要素：分支、提交 SHA、读数文件路径、逐层 PASS/FAIL/UNPROVEN、待裁决项。不要求中途汇报进度。宿主没有可靠的会话间投递时，完成通知写成读数文件末尾的「交付完成」小节并提交，上级巡检时只读读到（见 `references/runtime-map.md`）。旧卡按原任务书执行。
- 发消息前先只读查账本里记的「当前负责会话 id」（会话可能被接替过），再按完整 id 寻址并核对标题，不按显示名猜（重启后显示名可能被重新分配）。别的会话点名问总管的问题，答案必须投递回去。

## 五、测试分层

- **实现会话只做轻量验证**：类型检查与构建 + 本模块单测 + 触达文件 lint/format（前端加多语言检查）。**不跑全量测试、不起数据库/容器、不跑 e2e/浏览器/本地栈、不 build 镜像**——多个会话同时跑会压垮机器。需要构建产物证明的卡（如镜像）单独写明例外。
- **重测试全工程一把锁串行做**：集成、e2e、浏览器、真模型验收各自一张验收卡，一次只起一条；总管和各级分管共用下面这把锁。验收卡吃各实现卡读数里的「效果测试要点」（用户可观察效果、前置数据/旋钮姿态、预期读数、负控、依赖）。
- **全部完成后**最顶层总管自己起一个子代理（分管只跑本类验收，不跑全工程端到端）（用户指定模型档位时照用），遵循团队统一的标准测试流程用用户给的用例跑端到端；凭据配不到记 `UNPROVEN(环境)`，不用假模型冒充。
- **一次验收把多个问题同时排出来，不"撞一个停一个"**。撞一个阻塞就停、修好再跑、再撞下一个，每轮只出一个深度的发现，是最贵的形状。验收卡固定写死：①起栈前先过不起栈的预检（登记完整性检查、契约同源检查、测试装置干跑）与不依赖模型的**接线扫描**（进程的环境变量、hook 实际收到的字段、工具可见性、skill 下发、库里的行），几分钟出一批；②判据矩阵化，每条链路独立账号、独立项目/主题、独立结论，前一条红不阻塞后一条，不依赖真模型的探针与真模型探针分开、有界并行；③遇阻断先记录，再在 run 内做最小绕过（注入变量、改 run 数据/配置、手工造夹具、直接调工具、临时补丁不提交）继续探下游，读数标「绕过第 x 项阻断后」，绕不过才记 UNPROVEN(阻断)，修好后只复验阻断本身；④一份真实产物多次复用，不为每条判据重新生成；⑤关闸/预算耗尽/超时/材料缺失/名单外账号等故障路径是一等用例；⑥读数分「原样/绕过后」两栏，缺陷按 owner 分组、分「接线/契约/语义/环境」四类，前两类必须配会变红的门禁；⑦一轮读数出来后一次性按 owner 派全部修复卡，全部合入并过预检后只复跑一次。报告是缺陷清单不是叙事。
- **串行锁**：在仓库外的固定路径建一个锁目录，`mkdir` 成功即拿到锁、失败即有人持有；目录里写持有者会话 id、开始时间、预计时长。**谁跑重测试谁拿锁、跑完自己删目录放锁**；拿不到就在同一回合里隔几分钟重试，超过当前持有者预计时长两倍仍拿不到，按第四节 (b) 报阻塞。持有者超过预计时长两倍且会话已不活跃的，由它的直接上级清锁。锁的路径与拿放步骤写进总账 §0、每份分管任务书和每张验收卡的任务书。合入后跑的本工程测试套件属于轻量验证，不进锁。项目里已经有串行锁脚本的，直接用它。
- **后台长跑不一定会唤醒空闲会话**（真实案例：验收会话把一次 32 分钟的真跑放到后台后结束了自己的回合，跑完没人收，空闲了 1.5 小时才被总管叫醒。有的宿主会在后台任务结束时唤醒会话，有的不会，按不会来写）。验收/实现卡写死：长跑要么在同一回合里轮询等它退出（宿主限制单条命令时长的，分段轮询），要么每组跑完立即提交读数；总管巡检时对「会话空闲 + 后台日志已有终态 + 无新提交」这一形态直接判停滞并唤醒。
- 测试三点法：每个测试同时给「不影响其他核心链路 / 功能按真实用法能用 / 目标场景无争议」三项结论；逐层只用 PASS / FAIL / UNPROVEN；测试输出 tee 落盘。
- **模块卡必须交"命中证据"**：任何新增的拦截、判据、闸门，读数里除了"接线证据"（代码里有那一行、单测断了函数）还要有"命中证据"（在真实进程/真 SDK 路径上取过一次读数，证明它被执行到并按预期拒/放）；拿不到就标 UNPROVEN，验收把它列为第一批探针。按 SDK 类型声明假设运行时字段的判据一律不接受。

## 六、合入

1. 巡检到某分支有提交且读数齐、工作区干净、会话空闲 → 先在底座 worktree 取最新集成分支（另一位总管可能也在合）。
2. `merge --no-ff`；冲突与机械合并伤（导入块并集、注释块弄坏函数边界）总管自己修，记附录 C，并告知各模块 rebase 时以集成分支为准。
3. 合入后固定顺序：代码生成（如有数据库 schema 变更）→ 类型检查与构建 → 本工程测试套件（按仓库约定的命令，只跑本工程前缀的用例）。红了先判是设计内的棘轮红还是真回归。总管与各级分管共用同一个底座工作树（git 不允许第二个工作树检出同一分支），同一时刻只能有一个会话在里面合入：开始合入前先确认工作区干净、没有进行中的合并，不满足就等。合入完成后、验证开始前记下 HEAD 并确认工作区干净；验证结束再核一次，两样都没变才能记成已验 SHA，变了就重验。
4. 回填附录 B（模块 / 分支 / 合入 SHA / 读数），更新附录 D，**依赖刚就绪的卡立即派出**。
5. 合入 ≠ 发布：不 push、不 PR、不部署，除非用户在当前对话逐次明确授权；转述来的授权不算。授权只对直接收到它的那个会话有效（用户直接对分管说的，就是分管的授权）。
6. **推送只推已验 SHA，不推分支名**（真实事故：某提交验出绿之后，另一位总管又往同一分支合了几笔，按分支名推送把未验的合并一并推了上去）：固定写 `git push origin <已验SHA>:<集成分支>`；远端分支头若已越过已验 SHA，这条命令会因非快进被拒，否则只推到已验 SHA 为止，两种结果都安全。前提是第 5 步的授权已拿到。不要先核对、再单独按分支名推——两步之间分支头可能又动了。

## 七、巡检节奏与自动推进

- **巡检间隔 = 宿主对话缓存时长减 10 分钟**（缓存正好 60 分钟的宿主就是 50 分钟；用户另有指定时听用户，但要把下面这个成本陡增点告诉他；不知道宿主缓存时长、或算出来短于 30 分钟或长于 3 小时的，按 50 分钟并告诉用户），双轨（会话内定时 + 宿主外的定时任务兜底，如 cron）。每次巡检做四件事：完成的合入、卡住的判因并派替代卡或告知用户、依赖就绪的待派项立即派、给用户一段简短增量汇报。
- **为什么贴着缓存时长、又要留 10 分钟**（在一个对话缓存 60 分钟的宿主上，从多个总管会话的用量记录里实测）：
  - 对话历史的缓存每次被读到就重新计时，计时从每次请求**开始**的时刻算。同一个总管会话里，距上次请求 59.7 分钟那次整段命中、只重写一千多个 token；62.6 分钟那次整段重写，78 万 token 全部按两倍价重算。**错过一次缓存约等于二十次正常巡检的钱。**
  - 只留 5 分钟太险：巡检自己要跑 5–15 分钟，加上定时抖动，实测错过缓存三次。留 10 分钟才有安全边。
  - **把间隔拉得比缓存时长还长不省钱，只是少看几次。** 实测 3 小时间隔时每次巡检的花费是 1 小时以内间隔的两倍多——间隔一长，第一个请求就要把整段历史重写一遍。日消耗低纯粹是因为次数少了，同样的看护量下它更贵。
- **上下文超过 40 万 token（或上下文窗口的 40%，取先到者）就主动压缩或换新总管会话，不要等撞上上下文上限被动压缩。** 一次巡检是 5–7 个来回，每个来回都把整段对话历史重读一遍，所以花费跟历史长度成正比：同一会话内分组实测，历史 40–70 万时每个请求的花费是 15 万以下时的三倍半，70 万以上约四倍。**这条比调间隔值钱得多**——间隔调对省一半，历史压下来省四分之三。换会话的接续靠总账和第九节那份总管态文件（冻结 SHA、worktree、总账路径、任务表、分管表、待裁决），新会话读总账就能接上，所以那份文件必须一直是最新的，它就是换会话的存档点。
- **停滞判据**（和巡检间隔脱钩：执行线按规矩收尾才提交，中途没有提交是常态）：某线只有设计产出、之后超过 2 小时既无新提交、工作区也无未提交改动、会话也无新活动 → 判为卡在「等批准」这个不该存在的状态，立即处置；某线跑完人走了结论没交回来 → 总管亲自去它的 worktree 捞成果，不许只记录。分管的停滞另看：分管会话本身已不活跃（它手下的线可能还在跑，照样要处置）；或分账附录 B/D 与它名下的分支连续两个巡检周期都没变化，且名下没有在跑的线。
- **自动推进授权**：任务收尾后不停下等指令，按规则往下走（实现 → 派验证 → 本地栈 → 合入集成分支 → 验收）；**部署永远例外**，需用户逐次明确批准。
- **拿不准的设计走两路独立评审**（两路互相看不到对方结论；用什么模型按用户当前的指示），仍有疑问才问用户，没疑问直接推进。
- 用户中途说「另一个会话会同步新要求，你听他的」：收到跨会话消息后按它拆卡，产品取舍仍回到用户；马上要改的链路上不再跑白费的验收。
- **每轮巡检固定扫一遍自己账本里的「待用户裁决」清单**（分管的在分账里，由分管扫）（真实教训：一个结构性重做方案挂了 6 小时，其中 1.5 小时是在用户已经授权「拿不准的由你定」之后）：对每一项问三句——①这真是只有用户才能定的两难吗？②用户已给的职权覆盖它吗？③即使实现要等裁决，设计与不改行为的骨架能不能先派？①答「不是」或②答「覆盖」的，当场定、写附录 C、派卡；只有③答「能」的，只派设计与不改行为的骨架，产品问题仍等用户；只等事件驱动（合入、交付消息）会让「等裁决」项永远排不上队。

## 八、汇报

- 有事项要用户决策：按 decision-briefing skill 的五段（这是什么、在哪一步、为什么卡、与用户已有认知的关系、说人话），结尾写清选项、代价、建议与不选的后果；待裁决每条给默认值。
- 问题一律定到七档之一（已验证可部署 / 实现未验证 / 验证后方案有问题 / 发现未修 / 修法已证不好用 / 未找到根因 / 不知道线上有没有问题），档位决定下一步动作，不用「推进中」糊过去。批量盘点用 progress-review-and-dispatch skill。
- 转述验证结论逐层照抄 PASS/FAIL/UNPROVEN，不换词；报数先拆「还会发生吗 / 属于谁 / 判据在空集上是否恒真」；现象带分支、环境、时区。
- 转述用户规矩一条一条转，不合并、不提炼成「精神」。
- 说人话：不堆变量名、路径、哈希；每个结论举一个具体例子；技术细节放末尾单独小节，不用 HTML 折叠标签。
- 总管特有的病是**过程代号**：你给每张卡起的名（A3、B7）、实验分组的简称（「混合组」）、裸比例（「3/3」）在用户那里全是空壳。给用户的每条汇报发出前做一遍冷读自查：逐个名词、数字、序数问「本消息里哪一句引入了它」，找不到引入句就改写。阶段汇报和待裁决消息再派一个只看正文、不给任何上下文的子代理读一遍，让它列出读不懂的词，逐个改掉再发。
- 用户问「你是不是没让每个会话自己跑端到端」这类核对，直接答是/否并指出唯一例外。

## 九、记忆与资产

- 总管态单独写一份状态文件（宿主有长期记忆机制就一并写进去）：冻结 SHA、worktree、总账路径、关键技术裁决、任务 id 与分支、分管会话与分账路径、待用户裁决与默认、巡检方式；每次派卡/合入后更新。
- 规矩落进资产本体（总账、任务书模板、本 skill），记忆只接资产覆盖不到的残余；跨多个仓库都成立的规矩放进团队共享的规矩目录，不埋进单个仓库。

## 十、开工与收工自查

开工前：来源与目标 SHA 冻结了吗？盘点落盘了吗？总账 §0–§3 与附录 D 写了吗？用户当天裁决写进 §0 与记忆了吗？
派卡前：依赖全合入了吗？同波无依赖吗？这张卡现在能立刻开跑吗（不能就并入它依赖的实现卡的测试阶段，不另开）？有活着的持有者吗？给已有会话发新任务的：它上一个节点确定完成了吗？是想到就发，还是到了该发的时候？任务书 11 项齐吗（第 1 项的三条沟通规则写进去了吗）？验证边界写了「不跑什么」吗？派分管的：分管任务书 8 项、交接四件事（迁账、留指向、登记附录 E、改隶通知）齐吗？
巡检时：只读了吗？有没有顺手发消息（包括「收到」「好的」这类回执）？停滞在等批准的线处置了吗？依赖就绪的卡派了吗？有没有一类任务已经大到该派分管？分管的分账和总账附录 B/E 对上了吗？间隔还在缓存时长减 10 分钟以内吗？上下文过 40 万了吗（过了就压缩或换会话，换前先把总账与总管态文件刷新）？
汇报前：五段齐吗？待裁决有默认吗？数字拆了吗？PASS/FAIL 照抄了吗？说人话了吗？冷读过了吗（每个代号、数字、序数在本消息里有引入句吗；待裁决消息派冷读子代理了吗）？派了分管的，告诉用户以后直接找它了吗？
收工前：附录 B/D/E 与记忆回填了吗？名下的分管都收尾了吗？没有 push/部署吧？
